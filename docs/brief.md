# Промпт для Claude Code: каталог API, которые реально можно использовать коммерчески

> Как использовать: создай пустую папку проекта, положи этот файл как `docs/brief.md`, запусти Claude Code и напиши:
> «Прочитай docs/brief.md и начни с Фазы 0. Не начинай массовую проверку, пока я не подтвержу схему и пилот.»
> Рекомендуемая модель для основного прохода — Sonnet. Спорные случаи можно отдельно перепроверить Opus.

---

## 1. Цель

Создать открытый GitHub-репозиторий с курируемым списком публичных API, **данные которых можно использовать на коммерческом сайте**: с рекламой и партнёрскими ссылками, с хранением и публикацией данных на своих страницах.

Популярные каталоги ([public-apis/public-apis](https://github.com/public-apis/public-apis) и [public-api-lists/public-api-lists](https://github.com/public-api-lists/public-api-lists)) указывают только Auth, HTTPS и CORS. Лицензия MIT у них распространяется на сам список, а не на перечисленные API. Наш каталог закрывает этот пробел: по каждому API — проверенные условия с доказательствами.

Целевая аудитория: разработчики сайтов на открытых данных, programmatic SEO, инди-хакеры, создатели SaaS и AI-агентов.

## 3. Главное правило: только доказанное

Это проект о доверии. Одна выдуманная «зелёная галочка» обесценит весь список.

1. **Никогда не заполняй поля по памяти.** Каждое значение по условиям использования должно опираться на страницу, которую ты реально открыл в этой сессии (WebFetch, при необходимости Playwright).
2. **По каждому ключевому полю — доказательство**: URL страницы условий или лицензии, короткая дословная цитата нужного пункта (до 25 слов) и дата проверки.
3. **Нет доказательства — значение `unknown`.** Условия противоречивые или размытые — `ambiguous` с пояснением. Это нормальные, честные результаты.
4. **Разделяй два уровня**, они часто различаются:
   - **лицензия данных** (например, CC BY 4.0, public domain, ODbL);
   - **условия использования API** (например, «бесплатный эндпоинт только для некоммерческого использования»).
   Пример: у Open-Meteo данные под CC BY 4.0, но бесплатный публичный API только для некоммерческих целей, коммерческое использование — через платную подписку или свой развёрнутый сервер.
5. **Сайт с рекламой или партнёрскими ссылками = коммерческое использование.** Оценивай именно этот сценарий.
6. Это не юридическая консультация. В README обязателен дисклеймер.

## 4. Схема записи (черновик — уточни и согласуй со мной)

```yaml
id: open-meteo
name: Open-Meteo
url: https://open-meteo.com
category: Weather
description: ...            # краткое описание своими словами или из исходного списка (MIT)
auth: none | apiKey | OAuth
https: true
sources: [public-apis, public-api-lists]   # откуда взят

data_license: CC-BY-4.0 | public-domain | ODbL | proprietary | unknown
api_terms_url: https://...
commercial_use: yes | no | paid-only | ambiguous | unknown
storage_caching: yes | limited | no | ambiguous | unknown      # можно ли хранить без срока
redistribution_display: yes | no | ambiguous | unknown          # можно ли показывать данные на своих страницах
attribution_required: yes | no | unknown
rate_limits: "10,000 calls/day (free tier)"
bulk_download: yes | no | unknown
self_host_option: yes | no | unknown

verdict: green | yellow | red | unknown
#   green  — коммерческое использование, хранение и показ разрешены (возможно, с атрибуцией)
#   yellow — разрешено с существенными условиями (платный тариф, свой сервер, ограниченный срок кэша, share-alike)
#   red    — для коммерческого сайта не подходит
#   unknown — не удалось подтвердить

evidence:
  - field: commercial_use
    url: https://open-meteo.com/en/terms
    quote: "You may only use the free API services for non-commercial purposes."
notes: ...
confidence: high | medium | low
checked_at: 2026-11-21
checked_by: model-name or human
```

Хранение: один файл на API (`data/apis/<id>.yaml`) или единый `data/apis.json`. Обоснуй выбор с точки зрения pull request'ов и merge-конфликтов.

## 5. Фазы

### Фаза 0 — Подготовка (без массовой проверки)
1. Проверь лицензии обоих исходных репозиториев. Если там MIT, описания можно переиспользовать при сохранении уведомления об авторских правах. Сформулируй, как правильно указать атрибуцию в README и в `LICENSE`/`NOTICE`.
2. Предложи 3–5 вариантов названия репозитория (коротко, понятно, хорошо ищется). Например, в духе `commercial-friendly-apis`, `open-apis-for-business`, `license-checked-apis`.
3. Предложи стек:
   - парсер исходных README → нормализованный датасет;
   - генератор README из данных (README никогда не правится руками, только генерируется);
   - валидатор схемы для CI.
   Я предпочитаю Rust, но для скриптов допустим и другой вариант, если обоснован.
4. Согласуй со мной схему и формат README.

### Фаза 1 — Сбор и нормализация
1. Скачай актуальные README обоих репозиториев (зафиксируй commit SHA), распарси все записи.
2. Дедупликация по нормализованному URL или домену и названию. Сохрани информацию, из какого списка пришла запись.
3. Отметь мёртвые ссылки (HTTP-проверка) — их не проверяем дальше, но фиксируем.
4. Отчёт: сколько записей, сколько дублей, сколько мёртвых, распределение по категориям.

### Фаза 2 — Пилот (30 API)
1. Выбери 30 API из разных категорий, включая заведомо сложные случаи (Open-Meteo, TMDB, OpenStreetMap/Nominatim, NASA, какой-нибудь госсервис США, крипто-API).
2. Проверь их по правилам раздела 3.
3. Покажи мне результаты; я выборочно проверю 10 записей вручную. Только после моего подтверждения переходи к массовой проверке.

### Фаза 3 — Массовая проверка
1. Приоритет категорий: Government, Open Data, Geocoding, Weather, Environment, Transportation, Health, Science & Math, Finance, Food & Drink, Books, Business. Развлечения, игры, аниме, шутки — в конце или не проверяем вовсе (согласуй со мной).
2. Работай пачками по 20–30 записей. **Сохраняй результат после каждой пачки** и веди `progress.md` (что сделано, что осталось, проблемные случаи).
3. Страницы, которые не читаются простым запросом, пробуй через Playwright. Если условия за регистрацией или в недоступном PDF — `unknown` с пометкой.
4. **Вторая проверка:** все записи с `green`, а также все `ambiguous`, перепроверь отдельным проходом с установкой «найди причины, почему этот API нельзя использовать на коммерческом сайте». Расхождения — в `review-needed.md` для меня.

### Фаза 4 — README и репозиторий
README генерируется из данных и должен быть максимально удобным:
- короткое и цепляющее вступление: в чём проблема существующих списков и чем этот отличается;
- легенда вердиктов (🟢 🟡 🔴 ⚪) и пояснение каждого поля;
- **отдельный блок «🟢 Commercial-friendly»** вверху — главная ценность, ради которой придут люди;
- таблицы по категориям: API, описание, вердикт, коммерческое использование, хранение, атрибуция, ссылка на условия, дата проверки;
- счётчики: всего проверено, зелёных, жёлтых, красных; дата последнего обновления;
- машиночитаемый датасет (`data/` + собранный `apis.json`) — это отдельная ценность для разработчиков и AI-агентов;
- дисклеймер: не юридическая консультация, условия меняются, проверяйте перед использованием;
- атрибуция исходных списков;
- `CONTRIBUTING.md`: как добавить или обновить запись (обязательны URL условий, цитата, дата), шаблоны issue и PR;
- лицензия: код — MIT; данные — уточни со мной (например, CC0 или CC BY 4.0) с учётом того, что часть описаний взята из MIT-списков.

### Фаза 5 — Поддержка актуальности
- GitHub Action: валидация схемы и пересборка README на каждый PR.
- Еженедельная проверка ссылок; записи с `checked_at` старше 6–12 месяцев помечаются как «требует перепроверки».
- Опционально позже: простая страница на GitHub Pages с фильтрами по вердикту и категории.
